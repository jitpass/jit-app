AI Jobs

Let AI tools run list_guest_users.py in notion with 3 secrets. They see what it prints, never the values.

A job is a command you approved, with the secrets it gets. When an AI tool asks for one, the jit service runs it: it decrypts, starts the command in its folder, reads the output, hides the secret values in it, and hands back the text. The tool sends a name and gets a result. It never holds a key, so nothing in its process, its sandbox or its transcript can leak one.

Why this exists. Claude Desktop's Cowork shell is a Linux VM, and jit only runs on macOS. From the Mac, the whole VM is one process, so no grant can let the script in and keep Claude's own cat .env out. Terminal agents like Claude Code can reach jit already, but there the agent types the command, and jit run -- env is as easy as the real script. A job closes both gaps the same way. Cowork reaches it through jit mcp, terminal agents through jit job run.

Three rules the design forces, visible below. Only you approve a job, with Touch ID; an agent can only propose one. A job is fingerprinted, so a script or profile edited after approval stops running until you look. Every value jit injects is hidden in the output unless you mark it as safe to show. Design: jit/design/agent-jobs.md.

When a job changes

The folders Cowork opens are writable by the model, and that includes the script, its .venv and .jit/profiles. So the fingerprint is what keeps an approval meaning what you approved.

Where else AI Jobs shows up

Four places, each drawn on the surface as it ships today. The new part of each frame has a green tint so you can see what is added. The build does not keep the tint.

How the pieces map to the build

  • jit job allow
    What C does, from the terminal. Same sentence, same Touch ID. The app calls the same service op.
  • jit job run
    How terminal agents ask. Claude Code, Codex, Gemini CLI. No MCP needed: they already reach the service.
  • jit mcp
    How Cowork asks. A stdio MCP server that Claude Desktop starts on the Mac, with three tools: list_jobs, run_job, request_job. Connect in B writes it into Claude Desktop's config.
  • jit mcp install
    What Connect (K2) and the onboarding switch (M) run. The app runs the CLI through JitCLI, so the terminal can do it too. It backs up Claude Desktop's settings first and changes one entry.
  • jobs.json
    Where jobs live. Beside grants.json, in jit's own folder, which no sandbox is given. Never in a project, because a model can edit a project.

Worth a yes or a no before I build

  • 1
    Named "AI Jobs" in the app.Decided. The terminal command stays jit job: a command is typed, not read, and jit's other commands are single nouns.
  • 2
    Asks each time by default.Safer, and a proposed job always starts there. "Never" is one click away for jobs you want running while you are away, and it reuses the standing grant's own key. Recommendation: as drawn.
  • 3
    No arguments in v1.A job runs exactly what you approved. A date range or a user id would each need its own job for now. Later, typed parameters (a date, a pick-list) could be declared at approval, never free text. Recommendation: none in v1.
  • 4
    A separate window, not a Grants tab.A grant gives a program a key; a job never does. Putting them together would blur the one distinction this whole design rests on. Recommendation: its own window, reached from the panel (J), the Can run row on each agent card (K) and the Tools menu (L).
